# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

Built. `docs/NIXIE_PLATFORM_BRIEF.md` is the full spec for **Nixie**: a reusable NixOS platform with one installer ISO and two disjoint profiles (hardened Incus **server** host, Hyprland **desktop**). It is still the source of truth for what the platform must do, and this file only orients you within it. `ARCHITECTURE.md` says how it was built and every deviation; `VERIFICATION.md` is the record of what has actually been run, newest entry last.

- The design file is `design/Nixie Front Panel.html` — **with spaces**, not the underscores the brief writes. It is in the repo and tracked. Its `THEMES` object is the authoritative palette (the swatch cards beside it print a different Paper `s2`; `docs/design-tokens.md` says which to take), and the `tokens-from-design` check holds `ui/src/tokens/tokens.json` to it.

## Required process (brief section 15)

1. **Before any code**: write `ARCHITECTURE.md` (layout, full `nixie.*` option tree with descriptions, site contract, guest and data schemas, flake-input justifications, phase-engine diagram, installer state machine across reboots, desktop shell choice, every deviation from the brief with a reason). Ask at most five questions. **Stop for review.**
2. Implement in slices (a)–(l) in the order listed in section 15.2, one commit each, `nix flake check` green before every commit.
3. Never invent a NixOS option. Verify each against the pinned nixpkgs with `nix eval`, `nixos-option`, or the module source.
4. A slice is done only when its VM tests have actually run here. Each slice commits a `VERIFICATION.md`: commands run, pass/fail per test, artifact links, anything unverifiable and why. If KVM is missing, run under TCG and say so.
5. Conflicts between requirements, or with what nixpkgs can do: raise them with a proposed resolution, never pick silently.

## Commands

```
nix flake check -L                                        # gate before every commit; runs all checks incl. VM tests
nix build .#checks.x86_64-linux.<name> -L                 # one check
nix build .#checks.x86_64-linux.<name>.driverInteractive && ./result/bin/nixos-test-driver   # debug a VM test
nix run .#nixosConfigurations.<host>.config.system.build.vm   # quick host iteration
nix fmt                                                   # nixfmt-rfc-style; statix and deadnix also run in checks
nix run .#deploy -- --site <path> --host <name> <target>  # headless install over SSH
nix run .#test-iso                                        # boot ISO in QEMU (OVMF + swtpm) and drive the wizard end to end
```

Runtime CLI on an installed host: `nixie apply|fetch|restore|reseal|export|doctor`.

## Architecture (the parts that span many files)

**Platform vs site.** This repo is the platform and must contain nothing user- or hardware-specific (no service names, IPs, MACs, disk paths, interface names, board names, even in comments; `grep` for these is an acceptance check, hits allowed only under `tests/` and the example site's generated `hardware.nix`). A user's *site* repo holds `site.nix` (plain data), `guests.nix`, `data.nix`, `hosts/<name>/hardware.nix` (generated by the installer), and sops secrets. `lib.mkSite ./site.nix` does all wiring and yields `nixosConfigurations`, tofu configs, guest images, and checks.

**Flake outputs**: `nixosModules.nixie` (the `nixie.*` option tree), `lib.mkSite`, `templates.site`, `packages.{nixie-ui,nixie-setup,nixie-cli,nixie-iso,deploy}`, `checks.*`. Inputs target: nixpkgs, disko, lanzaboote, sops-nix, terranix. Any addition needs a one-sentence justification in `ARCHITECTURE.md`.

**One attrset drives everything.** `guests.nix` is the sole place guest names appear. From it derive the Incus instance (terranix), profiles/devices (`veth-<name>` nics, `shift=true` disks, gpu only when `gpu = true`), firewall chains, backup includes, scrape targets, dashboards, and the UI's declared list. Guests are either *declared* (in git, managed by `apply`) or *scratch* (created from UI or `incus launch`, never touched by `apply`, still gets default egress); the UI must label both and offer Export / Declare.

**Data root** (`nixie.data.root`, default `/data`): `state/<name>` irreplaceable and backed up; `cache/<kind>` re-fetchable via `data.nix` fetcher kinds (`hf`, `oci`, `incus-images`, `http`, plus site-added kinds) and never backed up; `media` per option. They never share a directory.

**Options are the UI.** Every `nixie.*` option's `description` is rendered verbatim by the installer wizard, so write it for a non-Nix person, sentence case, with consequences. Options carrying `nixie.ui.section` metadata become wizard steps. Everything optional (encryption, TPM+PIN, Secure Boot, attestation, duress, remote unlock, exit-node egress, Tailscale, monitoring, backups, host UI) is off by default and toggleable by `apply` without reinstall; only full-disk encryption requires reinstall and the CLI must refuse it with a clear message.

**One phase engine, three front ends.** `nixie-cli`/`deploy` implement eight idempotent phases with markers under `/var/lib/nixie/setup/` so any front end resumes after any reboot. The on-machine kiosk (cage + browser), the LAN wizard (`nixie-setup` on `:9443`, paired by code + cert fingerprint), and the headless `gum` wizard over nixos-anywhere are all front ends to the same scripts; the wizard may never do anything the CLI cannot. After first boot a NixOS *setup generation* specialisation carries the kiosk through phases 4–8, then deletes itself so no compositor or browser remains in a server closure.

**Profiles are disjoint.** `nixie.profile = "server" | "desktop"`, both under `profiles/`. Server closure has no compositor/browser/desktop package; desktop closure has no Incus/tofu/monitoring unless the site enables it. A `nix why-depends` check proves both directions. The security stack and installer are shared. Home-manager is allowed only inside the desktop profile, and only if the environment cannot be declared cleanly without it.

**UI and installer share one token set** extracted once from the design file (three finishes: Graphite, Umber, Paper). `nixie-ui` is a static TypeScript bundle served by incusd via `INCUS_UI`, everything vendored, `buildNpmPackage` with a committed lockfile, demo mode when no daemon is reachable. Host UI is Cockpit branded with the tokens, not a native agent.

## Style rules that are checked

- `nixfmt-rfc-style`, `statix`, `deadnix` in `checks`.
- Every platform-authored systemd unit passes `systemd-analyze security` at "OK" or carries a comment naming the required exposure.
- A check greps the closure for key-like material; no secrets in the store.
- Comments explain why, never what.
- Prefer nixpkgs modules over hand-rolled code, options over scripts, scripts in the flake over README instructions. One concern per module.
